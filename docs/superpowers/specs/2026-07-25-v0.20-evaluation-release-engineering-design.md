# v0.20.0 Evaluation & Release Engineering Design

## 1. 目标与边界

v0.20.0 在不改变现有运行时行为的前提下，把 Embedded Copilot 从可运行 Demo
升级为可评估、可展示、可发布的工程项目。新增能力位于独立的
`embedded_copilot.evaluation`、`web/` 展示层、发布文档和 CI；不得修改 Input
Layer、Supervisor、Integration Layer、Knowledge Gateway、Provider Contract、PCB
或 Datasheet Parser、领域 Agent、Agent API、已有 benchmark public models、
`EngineeringReport` schema 和 FastAPI contract。

Evaluation 是同步、离线、确定性的外部观察者：不新增 Agent、Parser、Provider、
Workflow node、LLM judge、外部服务、持久化、缓存或索引。它不读取附件内容，不扫描
目录，不保留 request、attachment metadata、文件名、路径、token、原始
`AgentResult`、PCB/Datasheet model、benchmark fixture body 或用户数据。

## 2. Evaluation 架构与数据流

```text
Synthetic BenchmarkDataset (3 end-to-end cases)
  -> EvaluationScenario
  -> EvaluationRunner
  -> injected SupervisorAgent.run(AgentTask)
  -> EngineeringReport validation
  -> deterministic metrics
  -> EvaluationReport
  -> JSON / Markdown renderer
```

`scenarios.py` 复用
`create_synthetic_embedded_copilot_integration_dataset()`，不复制 fixture 正文。每个
case 只允许 `end_to_end` category、synthetic marker、已知 expected Agent names 和
现有 `_benchmark_input_context`。Runner deep-copy case metadata，移除私有 context
字段，构造新的 `AgentTask`；context 必须先由 `UnifiedInputContext.model_validate`
验证，再通过现有 `attach_input_context` Supervisor adapter 注入。Evaluation 不直接
读取附件，也不调用领域 Agent。

`EvaluationRunner` 接受显式注入的 Supervisor-compatible target 和 monotonic clock，
按 dataset 顺序逐 case 执行一次，无并发、重试或 LLM fallback。它只接受 Supervisor
返回的成功 `AgentResult` 中可验证的 `EngineeringReport`；异常、失败 envelope、缺失或
无效 report 均转换为固定安全 failure code，并继续后续 case。空 dataset、非允许
scenario 或 report assembly 失败整体拒绝，不返回部分 `EvaluationReport`。

## 3. 内部模型、指标与确定性

`report.py` 定义 evaluation-only frozen Pydantic models，全部 `extra="forbid"`，
deep-copy 后验证 nested values：

- `EvaluationCaseResult`：`case_id`、`success`、五项 case metrics、总耗时、
  `agent_latency_status="unavailable"` 和安全 failure codes。
- `EvaluationMetrics`：routing accuracy、Agent success rate、report completeness、
  evidence traceability、平均/最大 total latency，以及
  `agent_latency_status="unavailable"`。
- `EvaluationFailure`：仅包含 `case_id` 和枚举化安全 code，不包含异常正文。
- `EvaluationSummary`：total/passed/failed counts 和整体 success。
- `EvaluationReport`：严格保持 `version`、`dataset`、`cases`、`metrics`、
  `failures`、`summary` 六个顶层字段。

指标定义如下：

| Metric | 确定性定义 |
|---|---|
| Task Routing Accuracy | `EngineeringReport.trace` 中 `agent_planned` 对应 Agent 集合与 case expected agents 的交集数除以并集数；两者为空时为失败 |
| Agent Success Rate | `agent_executed` 事件中 `status="success"` 的数量除以 planned Agent 数量；缺失 planned events 时为 0 |
| Report Completeness | expected agents 对应的 Hardware/Firmware/PCB/Debug section 存在数除以 expected section 数；不要求无关 section |
| Evidence Traceability | report summary、存在的 sections、findings、recommendations 均具有通过 `EngineeringReport` 验证的 `source_agent`/`source_id` 时为 1，否则为 0 |
| Execution Latency | monotonic clock 直接观测单次 Supervisor 总耗时；逐 Agent timing 固定标记 `unavailable`，不估算、不补埋点 |

case 成功要求前四项质量指标均为 `1.0` 且 Supervisor/report 有效；latency 仅观察，
不参与 pass/fail。聚合比例按所有 case 等权平均，耗时使用毫秒并固定 round 到 6 位。
注入 fixed clock 时，model、canonical JSON 和 Markdown 必须 byte-for-byte 一致；真实
clock 下同一已生成 model 的渲染仍必须一致，但不同运行的实测耗时允许变化。

JSON 使用 UTF-8、固定字段顺序、稳定缩进和结尾换行；Markdown 使用固定 section 与
case 顺序。Renderer 先 deep-copy 并重新验证 `EvaluationReport`，不输出 case input、
metadata、异常、`EngineeringReport` 正文或 trace 明细。

## 4. Demo 与发布体验

`web/app.py` 保持 API client 是分析入口，不 import Supervisor、Agent、Parser、
Knowledge Gateway 或 EvaluationRunner。侧边导航提供四个视图：Overview、Workbench、
Benchmark、Example Report。Workbench 保留 v0.19 metadata-only 上传与 API workflow。

- Overview 展示简洁项目定位、Requirement -> Knowledge -> Planning -> Agents -> Report
  workflow 和当前技术栈。
- Benchmark 展示内置安全 `EvaluationReport` projection 的 Cases、Success Rate、Total
  Latency、Coverage；不执行 benchmark，不显示 fixture body。
- Example Report 展示静态、已验证、可追溯的 ESP32 Camera `EngineeringReport`；仅含
  安全摘要、结构化 section、evidence 和 source identifiers，不含源码、PDF 正文、PCB
  原始数据或附件路径。

展示逻辑拆为纯 projection/helper 模块，以便不启动 Streamlit server 即可单测；页面
之间不嵌套业务逻辑，也不改变 FastAPI request/response。

README 按 Overview、Architecture、Features、Demo、Benchmark、Installation、Deployment、
Engineering Design、Limitations 重构，并明确系统不会自动修改 PCB、自动烧录、替代
EDA DRC 或人工审核。`docs/release/v0.20.md` 记录 Version History、Architecture、
Benchmark Results、Known Limitations 和 Future Roadmap；benchmark 数值只写入经本地
验证得到的结果，不编造 Docker 或 CI 运行结论。

## 5. CI、版本与验证

新增单一 GitHub Actions quality gate，使用 Python 3.11 和现有依赖，依次执行 pytest、
compileall、Ruff 及 schema compatibility tests，不接入外部服务。版本在
`pyproject.toml`、package `__version__`、settings/health schema、README 和相关 contract
tests 中统一为 `0.20.0`；仅版本 literal 变化，不改变 Health response shape。

测试采用 TDD，覆盖指标边界、失败隔离、单次顺序执行、Supervisor adapter 注入、
frozen/extra-forbid/deep-copy、fixed clock、JSON/Markdown determinism、安全 redaction、
四个 Web 视图、API contract、示例报告 provenance、版本一致性、README/release 引用和
CI command。先运行 focused suites，再执行请求指定的相关回归、完整 pytest、compileall、
Ruff 和 `git diff --check`。

若 Docker CLI 可用，执行 build、compose config 和 compose up 后验证 health；若不可用，
只静态检查 Dockerfile/compose 引用、copy paths 和命令，并在最终报告明确未执行运行时
容器验证。完成后创建本地提交 `feat: add evaluation and release engineering`，不创建
tag、不 push；推荐但不创建的标签为 `v0.20.0`。
