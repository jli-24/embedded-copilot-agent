# Embedded Copilot v0.46.0

## Release Overview

v0.46.0 adds a framework-independent Execution Integration Layer between verified
agent output, human-reviewed proposals, caller-owned executors, and verification.
It provides controlled execution contracts and deterministic fake-based validation;
it does not add a production executor or any real engineering operation.

## Execution Integration Architecture

```text
SUCCESS AgentExecutionSnapshot + ProposalProjection
  -> ExecutionPreparationRequest
  -> Execution Plan
  -> exact Executor Registry Boundary
  -> READY ExecutionSnapshot
  -> Human Approval Binding
  -> Controlled Execution Lifecycle
  -> Verification Projection
  -> terminal ExecutionSnapshot
```

The `ExecutionRuntime` facade exposes only `execution_port()`. Runtime dependencies
are injected through Protocols, remain private, and cannot be recovered from public
plans, snapshots, progress events, or fingerprints.

## Executor Registry Boundary

Preparation performs one exact registry resolution for the caller-selected
`BUILD`, `FLASH`, `DEBUG`, or `VERIFY` executor type. The Runtime does not infer an
executor from artifact metadata, discover implementations, dynamically import a
provider, or fall back after a binding failure. Live executor identity remains in a
private process-local binding.

## Execution Plan

The Execution Plan binds caller-owned execution, workflow, task, and agent IDs to a
safe context projection, proposal ID and fingerprint, explicit executor type, UTC
timestamp, and deterministic SHA-256 fingerprint. It contains no raw context,
artifact body, command, path, stdout, stderr, or provider configuration.

## Human Approval Binding

Execution requires a deep-copied and revalidated typed `HumanReviewSnapshot` in the
`APPROVED` and `COMPLETED` state. Proposal identity and fingerprint, reviewer,
review timestamp, execution ID, and READY snapshot fingerprint must all match.
Rejected review returns cancellation; requested changes require a new proposal and
new execution ID.

## Controlled Execution Lifecycle

The deterministic lifecycle is:

```text
CREATED -> READY -> APPROVED -> RUNNING -> VERIFYING -> SUCCESS
```

Executor, timeout, verification, denial, and revision outcomes terminate as
`FAILED`, `TIMEOUT`, or `CANCELLED`. The Runtime does not retry, recover
automatically, or continue after required progress delivery fails.

## Verification Projection

Every structurally valid executor result is passed once to the injected verification
Port. Verification must bind the same execution ID and result fingerprint. Only a
successful result with `VALID` verification can produce a `SUCCESS` snapshot.

## Failure Snapshot

Operational failures produce immutable terminal snapshots with allowlisted failure
codes. They do not expose provider exceptions, commands, paths, output streams,
logs, credentials, or traceback data. Illegal contracts, mismatched bindings, replay,
and progress failures raise sanitized boundary exceptions instead of partial state.

## Replay Protection

Each execution ID is reserved for the Runtime lifetime. A READY binding is consumed
atomically on the first valid Human Review decision, so sequential and concurrent
replay cannot invoke the executor twice. The ledger is deliberately process-local;
cross-process replay protection is not claimed.

## Progress Event Isolation

Progress events contain only sequence, execution and workflow IDs, event, state,
and caller-provided timestamp. Progress sink failure is fail closed, is not retried,
and does not return a partial snapshot.

## Security Boundary

The Runtime has no framework, API, Agent implementation, Supervisor, Workflow,
Knowledge, Engineering Memory, Tool Runtime, Workspace, database, network, Shell,
Git, filesystem, or hardware SDK dependency. Typed upstream contracts are preserved
through deep copy and revalidation without a serialization round-trip.

## Validation

Release validation covers contract immutability, exact binding, approval lifecycle,
safe result verification, terminal failure mapping, sequential and concurrent replay,
progress fail-closed behavior, static security boundaries, protected Runtime
regressions, the full offline pytest suite, Ruff, scoped Black, compileall, pip check,
Git diff validation, version drift checks, and protected-source hash verification.

Release candidate evidence:

- Execution Runtime focused/security: 29 passed
- protected Runtime regression: 375 passed
- complete security regression: 128 passed
- full pytest: 2339 passed, 6 skipped
- Ruff, scoped Black, compileall, pip check, and Git diff check: passed

## Non Goals

v0.46 does not provide real Build, real Flash, real Hardware Debug, Shell, Git,
network access, filesystem mutation, hardware control, a production executor,
background execution, persistence, automatic retry, or cross-process replay
protection. Passing deterministic tests is not a claim of hardware validation or
production execution readiness.
